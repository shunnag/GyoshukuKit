# GyoshukuKit 0.6.0 release preparation, part 1 — 2026-09-27

Base: `feature/2026-09-24-review`, HEAD `5b52710`. This preparation changes no
production Swift source. No commit, push or tag was made, and neither sibling
repository was modified. Release order: KaitoKit 0.11.0, GyoshukuKit 0.6.0,
KaitoFinder 0.4.0.

## Release edits

- The non-sibling dependency is `.upToNextMinor(from: "0.11.0")`, i.e.
  `0.11.0 <= version < 0.12.0`. The sibling selection code is otherwise identical
  to HEAD. SPI use is outside SemVer guarantees; KaitoKit types also appear in
  GyoshukuKit's public API.
- CHANGELOG has an empty Unreleased section followed by 0.6.0 dated 2026-09-27.
  Output-byte and existing-caller behavior changes are collected under 変更.
  README and design documentation describe the versions, dependency range,
  updaters, batch additions and progress.
- Both ZIP modern-method test files now read `Tests/Fixtures/zip-modern` locally.
  All seven base64 files match KaitoKit commit `26b84ca` byte-for-byte, and their
  decoded SHA-256 hashes match its manifest. No remaining test file reads a
  sibling KaitoKit fixture. KaitoKit's top-level NOTICE has no zip-modern entry;
  the fixture-specific README provenance was copied into our NOTICE with that
  source explicitly identified and the seven archive hashes retained.

## Public-repository hygiene and frozen inputs

- Scanned the current contents of every path changed by a commit since v0.5.0,
  plus this preparation's changes and new files. Home-directory prefixes became
  `~`; scratchpad prefixes became `$SP`. Redactions affected 25 existing
  verification files. The Python benchmark helper now reads `SP` from the
  environment, so the redacted path remains usable.
- No matching literal paths remain in that scope. No frozen-input exceptions
  were needed; decoded base64 fixtures were also checked for the same literals.
- All 37 files in `Tests/Fixtures/sevenzip-edit` remain byte-identical to HEAD,
  including `bcj.7z`, `bcj2.7z`, `ppmd.7z` and both expected-value JSON files.
  Their payload/provenance replacement is deferred to part 2.
- `lha-updater/manifest.json` is decoded by `LHAUpdateSupport.fixture`; tests hash
  decoded archive bytes, not the manifest. Only `referenceReader.version` was
  corrected from the unpublished 0.12.0 label to 0.11.0. Its commit, source-tree
  hash, fixture lengths and all archive hashes are unchanged. The fixture README
  records this metadata correction.

## Swift 6.3 と macOS 26 での確認（2026-09-27〜28）

手元は macOS 27.2・Swift 6.4 だけのため、KaitoKit の診断用 draft PR #36（`ci-debug/splice-crash`、マージしない）に
job を置き、GitHub の macos-26 runner（macOS 26.6.2、Xcode 26.6、Swift 6.3.3）で `release/0.6.0` を
隣接 path 依存（KaitoKit `release/0.11.0`）で build・試験した。

1. 本体が Swift 6.3 でコンパイルできなかった 2 点を直した（`756a5cf`）。
   `ZipCentralDirectory.CopyValidator` は private の stored property を持つため memberwise init が private になる。
   `CompressedTarUpdater` の `@_spi(Testing) @TaskLocal public static var testingFault: Fault?` は、6.3 の macro 展開が
   `$testingFault` に @_spi を付けず SPI の型を公開の宣言で使う。`Fault` と試験用の task-local 3 つを internal にした。
   `756a5cf` の commit message の「KaitoFinder の試験は使っていない」は誤りで、KaitoFinder の
   `CompressedTarVerificationFailureTests` が `$testingFault` / `$testingSkipsSelfCheck` を使っていた。
   KaitoFinder 側の import を `@_spi(Testing) @testable import GyoshukuKit` にした（KaitoFinder `7431500`）。
2. 同じ commit で、`ArchiveRewriter.open` が KaitoKit 0.11 の `CancellationError` を
   `RewriterError.invalidArchive` に包んでいたのを直した（取消し済みの Task から開く試験を追加。修正前は失敗）。
3. 試験が Swift 6.3 でコンパイルできなかった点を直した（`8de090c`、`766bef0`）。`(0..<8).first { ... } ?? 8` の推論と、
   `Task.detached` の closure 内の `Self.`（region-based isolation checker が検査できない）を class 名にした。試験の内容は同じ。
4. macOS 26 での実行（`766bef0`、`brew install sevenzip xz lhasa`）: 584 件、skip 18、失敗 4（想定外 3）。
   3 件は実行環境による試験側の失敗で、ライブラリの失敗はない。
   - CP932 の名前を `ditto -x` で展開する 2 件: ditto は UTF-8 の flag のない名前を `~/.CFUserTextEncoding`
     （手元は日本語、runner は英語）で解釈する。
   - `TarUpdaterInteropTests`: runner には GNU tar があり（手元にはない）、libarchive の xattr の pax keyword の警告が出力に混ざる。
   `lha` は Homebrew の `lhasa` の formula が入れる（`lha` という formula はない）。
   これらの試験の修正と CI（macos-26 と xcode-27、tag 参照）は、公開の後に branch `ci/minimal` から PR にする。
   同じ runner での `ci/minimal` の結果: 584 件、skip 18、失敗 0。
5. 手元（macOS 27.2、Swift 6.4、隣接 path 依存、KaitoKit `e860988`）の最終候補 `766bef0` の全件: 584 件、skip 18、失敗 0。

macOS 26 の Foundation の Data の不具合（位置 0 でない空の slice へ空の内容を汎用の `append(contentsOf:)` で足すと trap する）に
当たる箇所は、Sources と試験を静的に監査して見つからなかった（KaitoKit の検証記録
`2026-09-27-release-preparation-0.11.0.md` に条件を記載）。
